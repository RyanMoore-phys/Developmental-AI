### 1. [CRITICAL] Lifelong loop never resets a crash-rebuilt MineRL client — the stream wedges permanently on frozen frames
- **file:** `developmental_ai/core/developmental_loop.py:2873`  (pass 1, conf=high)
- **claim:** When a MineRL client dies mid-step, the adapter catches it, rebuilds the client, and returns (stale_obs, r, terminated=False, truncated=True, {'env_restarted': True}) expecting the caller's autoreset (minerl_env.py docstring lines 36-38: 'step() truncates the episode ... and the caller's autoreset lands on the fresh client'). The lifelong loop breaks that contract: line 2873 `dones.append(bool(term) or _rst)` classifies the adapter-caught crash (term=False, trunc=True, _rst=False) as a plain time-truncation, so the ADVANCE block (3147-3163) takes the `else: obs_list[e_i] = next_obs_list[e_i]  # truncation carries on` branch and NOBODY ever calls reset() on the rebuilt client (_rebuild() at minerl_env.py:318-325 only constructs the env object; MineRL launches the mission inside reset()). Every subsequent step() on the never-reset client fails, the adapter catches it again, rebuilds again, and returns the same stale pre-crash frame with truncated=True — forever. The `env_restarted` info flag is set at minerl_env.py:380 and consumed nowhere in the repo (grep confirms). The loop-level timeout path has the same hole: lines 2855-2864 set restarted=True and line 3157-3158 carries the stale obs with the comment 'wrapper rebuilt it', but the wrapper rebuilt only the CLIENT, not the mission — no reset there either (plus the timed-out future keeps running, so the next submit can call step() concurrently on the same adapter). Side casualties for the adapter-caught path: dones=False means death_reset() (3152) and _mine_by_env.pop (3153) never run, so the RSSM row and mine high-water marks also go stale.
- **evidence:** developmental_loop.py:2869-2873: '# LIFELONG: the STORED done is the TERM-FLAG ... A plain 8000-tick time-TRUNCATION is NOT a boundary ... deliberately excluded here.' / 'dones.append(bool(term) or _rst)'. developmental_loop.py:3147-3163: reset happens ONLY in the `dones[e_i] and not restarted[e_i]` branch ('o, _ = envs[e_i].reset()  # success -> fresh world'); the trunc path is 'obs_list[e_i] = next_obs_list[e_i]  # truncation carries on'. minerl_env.py:374-380: 'except Exception as e: ... self._rebuild(); return self._last_obs(), total_reward, False, True, {"env_restarted": True}'. minerl_env.py:318-325: _rebuild() = close() + _make_underlying(), no reset. In lifelong mode the adapter can NEVER emit a legitimate time-truncation (TimeLimit removed, minerl_env.py:247-249), so truncated=True from a MineRL adapter always means crash-restart or an underlying done — both hard boundaries requiring reset.
- **impact:** MineRL Java clients 'die/hang after hours' by the adapter's own documentation (minerl_env.py:34-38), so this fires with near-certainty during a multi-day lifelong run. A wedged scout feeds a constant frame and zero reward into the world model, LP curiosity, and goal discovery for the rest of the run; if env 0 wedges, PPO, the vision magnet, seek-shaping, and the entire developmental stream silently train on a single frozen image with zero extrinsic reward — the run looks alive but learning is dead. This is the single largest threat to 'fully learn Treechop as a lifelong stream'.
- **fix:** In the lifelong ADVANCE block, treat a MineRL truncation as a death boundary: if step_infos[e_i].get('env_restarted') (or simply trunc==True on the MineRL adapter under lifelong), submit envs[e_i].reset() through self._env_pool with reset_timeout_s (reuse the _bounded_rebuild pattern from _parallel_reset), then death_reset(e_i), _mine_by_env.pop(e_i), option_executor.clear(e_i), and for e_i==0 also clear _prev_mine. Alternatively have the adapter's crash path reset the fresh client itself and return the new world's first obs with truncated=True. Keeps env 0's stream continuous (a crash is a genuine boundary, not an imposed one) and honors all hard constraints.

### 4. [HIGH] Zero-clamped LP + zero-inflated std normalization turns prediction-error noise into persistent, farmable intrinsic reward on mastered scenes — curiosity never quenches
- **file:** `developmental_ai/curiosity/learning_progress.py:155`  (pass 1, conf=high)
- **claim:** LP has no significance gate: any error drop, however tiny, pays. For a mastered bucket (flat error + stochastic jitter) the older-half mean exceeds the recent-half mean on ~half of visits purely by chance, so E[LP]>0 forever on fully-learned recurring scenes. The normalization then AMPLIFIES these chance ticks: the running pool is dominated by zeros (scout singleton buckets + immature buckets; 4 streams share one 1000-sample deque = only ~250 loop-steps), so median≈0 and std is on the order of the noise ticks themselves — chance ticks normalize to O(1..5) and real drops saturate at the 5.0 clip, making delivered LP near-binary. The clamp-at-zero means noise has strictly positive expectation. The code's own safety argument ('LP is mostly zeros ... no all-positive baseline to farm', lines 170-173) is false in the lifelong regime where the primary dwells in established buckets.
- **evidence:** learning_progress.py:150-155: `if len(hist) >= self.lp_min_samples: ... older = float(h[:half].mean()); recent = float(h[half:].mean()); lp[i] = max(0.0, older - recent)` — at min_samples=4 this is a 2-vs-2 mean comparison, positive ~50% of the time under flat error. learning_progress.py:175-177: `if self._running_std > 1e-8: reward = (reward - self._running_median) / (self._running_std + 1e-8); reward = torch.clamp(reward, 0.0, self.reward_clip)`. icm.py:366-375 (_update_stats): std computed over a mostly-zero 1000-sample pool fed 4 values/step (developmental_loop.py:2931: `intrinsic = self.curiosity.compute_intrinsic_reward(obs_t, action_tensor, next_obs_t)` over all 4 envs). Consumption at weight 0.7: developmental_loop.py:3112 `mixed = self.reward_mixer.mix(float(intrinsic[0].item()), prim_extrinsic)`.
- **impact:** This corrupts the system's central drive. A chance tick delivers ~0.7 x (1..5) x 0.62 ≈ 0.4-2.2 mixed reward, comparable to or exceeding the mixer-weighted first-log event (0.3 x 6 = 1.8) and dwarfing the 0.004 seek nudge — PPO can maximize return by parking in familiar scenery (consistent with the observed foliage plateau). Because mastered scenes keep paying, curiosity never anneals to zero the way the design intends ('mastered then -> 0, and the agent moves on'), the gated mixer's natural anneal is undermined, the 'Intrinsic reward' metric people steer by stays inflated, and the magnet's cat_lp/global_lp EMAs (vision_scaffold.py:361-366) absorb noise credited to whatever is on screen.
- **fix:** Significance-gate LP: require the drop to exceed k x the bucket's own error std (e.g. Welch-style, or a fixed fraction of the bucket's mean error level), and/or subtract the bucket's expected chance-LP baseline E[max(0, delta)] under a flat-error null. Independently, floor _running_std at an absolute epsilon (or normalize by a robust scale of the NONZERO subpopulation) so a quiet pool cannot amplify noise ticks to O(1). Both preserve the natural anneal — they remove only the noise floor, not the schedule.

### 6. [HIGH] Seek drive is economically incapable of unparking the agent: non-goal park pays 20-40x the nudge, and the nudge itself pays the parked attack+forward action
- **file:** `developmental_ai/llm/vision_scaffold.py:332`  (pass 1, conf=high)
- **claim:** The seek drive's stated purpose (config comment: 'unsticks the agent from parking on stone while no tree is visible') is arithmetically impossible with shipped constants, and its two mechanisms are broken in opposite ways: (1) while a tree is fully off-screen the head's tree prob sits at ~0, so the seek potential 0.5*(gp - prev) is a flat-zero plateau with no directional gradient — it only pays once a tree already edges into frame; (2) the only off-screen driver, the 0.004 forward nudge, is dwarfed by the standing shaping income for staying parked at a trusted non-goal object.   The anneal REPORTS a near-balanced 0.54/0.46 while the RETURNS are 582:1. (Down from the 1922:1 measured before the occlusion fix and tier changes — the improvement is real and insufficient.)

### 75. [MEASURED 2026-08-23] The 200 ms/step is OP COUNT, not compute — and the policy may be taking one gradient step every five minutes
- **how this started:** "why are we at 3.2 steps/s against a 10 steps/s ceiling, and what owns the ~200 ms of non-environment time?" The server ticks at 20/s and `action_repeat: 2`, so Minecraft accounts for ~100 ms of a ~300 ms step. Two thirds is ours.
- **PROFILED on the LIVE modules at the LIVE config** (real objects, `torch.profiler`; aten-op counts are device-independent and are what drives launch overhead):

  | per-step call | aten ops | CPU ms |
  |---|---|---|
  | `LearningProgressCuriosity.train_step` | **1519** | 29.6 |
  | `compute_intrinsic_reward` | 295 | 9.0 |
  | `world_model.encoder` + `rssm.observe_step` | 275 | 11.0 |
  | `policy.select_action` | 260 | 2.9 |
  | **per env step** | **~2350** | — |

  plus **~25 CPU<->GPU sync points per step** (13 loop body, 8 `select_action`, 3 `train_step`, 1 `compute_intrinsic_reward`).
- **the finding:** nothing here is a big model. The whole curiosity module is **1.25M params with a CNN encoder**; the world model is 54.1M but runs one GRU timestep under `no_grad`. The cost is **~2350 tiny GPU operations at batch num_envs=2, plus ~25 pipeline drains, every step** — which is exactly the recorded "GPU utilisation 2% while we burn 200 ms/step" signature. The device is idle; we are paying launch and sync latency.
- **A MEASUREMENT TRAP I FELL INTO FIRST, recorded because it is the same family as the container-vs-host one:** my first profile built `IntrinsicCuriosityModule` without `pixel_obs`, measured a **12.65M-param dense MLP on 49,152 raw pixels**, and produced a confident "smoking gun". The live constructor passes `pixel_obs=bool(self.pixel_obs and cur_cfg.get("cnn_encoder", True))` — the CNN path has been on all along. **Measure the object the agent actually runs, not the one the constructor defaults to.**
- **SHIPPED (staged, not pod-proven):**
  * **A1 — batched curiosity training.** `curiosity.train_every` (default 1 = byte-identical). Accumulates K transitions, one update on the concatenated batch: 1519 -> 380 ops/step at K=4, -> 95 at K=16. BATCHES, never SKIPS — forward-model error IS the curiosity reward, so training less often would slow novelty decay, a reward-economy change. Safe because `LearningProgressCuriosity` does not override `train_step` (LP bucket/history bookkeeping is all in `compute_intrinsic_reward`, which stays per-step). One shared `_curiosity_train` helper serves all THREE stepping bodies, so this feature cannot drift between duplicated bodies.
  * **A3 — one device->host transfer per action.** `select_action` did three `.item()` calls (action, log_prob, value) on every env step; each blocks the CPU until the GPU drains, and the VLM shares that device, so a drain can wait behind a 1.5 s inference. Now one fused `torch.stack(...).tolist()`. Exactness asserted against the unfused computation.
  * **A2 — reuse the encoder forward across the step boundary.** `arch: wm` means the policy encodes through `world_model.encoder` — the same module the loop already ran on that frame one step earlier as `encoded_next`. Now handed forward EXPLICITLY (not cached). **Validity is decided by an IDENTITY test** on the observation arrays: an env that kept running had `obs_list[e] = next_obs_list[e]` assigned, so the two are the same object; an env that reset holds a fresh array. Inferring it from the branch conditions (`dones[e] or _crashed`, plus a timeout path that carries the obs anyway) is how it would eventually serve a pre-rebuild frame silently. Ships with `verify_encoder_feats: true` — recompute-and-compare on every use, raising above one optimizer step of async encoder drift — so the first live run PROVES it before the check is turned off for the speedup.
- **THE BIGGER FINDING (B1) — a starved policy was being reported as a healthy one.** PPO's tiny-batch collapse guard caps epochs at `rows // 32`. Under SMDP options one stored ROW spans tau env steps, so with `n_steps: 1024` and `max_option_steps: 80`:

  | tau | rows per update | epochs run |
  |---|---|---|
  | 20 | 51 | 1 |
  | 40 | 25 | 1 |
  | 80 | 12 | 1 |

  At 3.2 steps/s that is **one full-batch gradient step on 12-51 samples every ~5.3 minutes — roughly 270 per day.** The guard itself is correct and must stay (10 epochs on ~25 rows once crushed the option logits into a self-locking policy: ~38,940 masked draws, zero option picks). But it prevents collapse by REMOVING UPDATES, it logged that at `DEBUG` (i.e. never, in production), **and the loop's segment print annotated any `epochs_run < n_epochs` as "stopped early (good: the policy hit its movement budget)"** — which describes `target_kl` early-stopping. `target_kl: 0.0`, withdrawn 2026-08-05. **So the only reachable cause of that line was starvation, and it was labelled good.**
- **why this matters beyond throughput:** finding #73 recorded a dissociation — the world model learning steadily over 47 segments while the policy acquired nothing — and attributed it to the reward economy (582:1). This is a second, independent candidate cause: the WM gets ~4 updates per 1000 steps on 16x16 batches, asynchronously; the policy gets one full-batch pass over as few as 12 rows. **One of the two learners is being fed and the other is not.**
- **NOT YET PROVEN LIVE.** Row count depends on the actual option/primitive mix, and competence gating has held option invocations low at times (0 for all 16 skills once, 34 later), which would mean mostly primitive rows and tau~1. The arithmetic establishes the RISK, not the fact — which is why B1 shipped as instrumentation only: `PPO STARVED` at WARNING, `epochs_capped` in the metrics, and a segment line printing the row composition (option vs primitive, mean tau). **No PPO tuning until that has run.** If it shows rows are plentiful, the guard is not binding, #73's explanation stands alone, and this is dropped — which is a success for the diagnostic, not a wasted step.
- **tests:** `tests/_throughput_wave_smoke.py`, 22 contracts (A1 batching/detach/no-drift, A2 exactness + wrong-frame refusal + identity invalidation, A3 exactness + sync count, B1 forensics + the STARVED-before-good ordering). Full sweep re-run for regressions.

### 76. [MEASURED 2026-08-23] The data diet: a 10-hour memory that dies on every crash, and a training window too short to contain a tree-break
- **the question:** "the world model is on a thin data diet — how do we widen it?" It turned out to mean FIVE independent things, only one of which is the sample rate everyone assumes. Each measured against the live config.
- **W1. A TRAINING SEQUENCE COULD NOT CONTAIN A TREE-BREAK — the finding that matters most.** `sequence_length: 16` at `action_repeat: 2` spans **32 GAME TICKS**. Measured `Ticks-to-break` from the live logs: dirt/grass are 20-22t and fit comfortably; a **barehanded log needs ~60t**. So the world model had *never seen a complete log-break as one trajectory* — only its first half or its second half. We have spent months asking it to learn an event that does not fit in its window.
  * FIX: `batch_size 16 -> 8`, `sequence_length 16 -> 32`. 8x32 = 256 transitions, **identical to 16x16**, so the obs tensor (50.3 MB) and the measured 1.59 GB training step are unchanged — temporal span bought at CONSTANT memory, which matters because VRAM is shared with the VLM's ~5 GB. Span is now 64 ticks, clearing 60 with margin.
- **W2. REPLAY RATIO 65.5 vs DreamerV3-on-Minecraft's ~512.** `train_iters:128 x 16x16` per (`wm_train_every:250` x 2 envs). We were ~8x under-training on data ALREADY COLLECTED, on a GPU measured at **2% utilisation** with the async trainer reporting **`skip 0.0%`** — never behind. `train_iters 128 -> 384` lifts it to 196.6. Not straight to ~512: the ratio is only safe alongside a buffer big enough to feed it. The governor is the existing `AsyncWM replay-ratio: N/M blocks run (skip X%)` line — past ~10% skip the trainer has stopped keeping up.
- **W3. MEMORY HORIZON 10.4 HOURS.** `buffer_capacity` is **split across streams** (`per_stream_cap = capacity // num_streams`), so 240k with 2 bodies gave each 120k transitions = 10.4 h at 3.2 steps/s. Everything older was overwritten — on a box with **125 GB of RAM** where the buffer used **11.8 GB**. Raised to 1M (500k/stream ~ **43 h** each, ~49 GB). Note the perverse incentive this created: *adding a body SHORTENED the brain's memory*.
- **W4. THE MEMORY WAS VOLATILE — `ReplayBuffer` had NO save/load path at all.** The supervisor relaunches automatically on process death, and live Python exceptions have caused exactly that. Every relaunch restarted world-model training from an **EMPTY buffer**, so the effective diet was never the configured capacity; it was *"however long since the last crash"*.
  * FIX: `save()`/`load()` on `ReplayBuffer` + the multi-stream wrapper, stored in **chronological** order (not the raw circular layout) so a restore survives a capacity change — the newest `min(n, capacity)` are kept, exactly as the circular buffer would have dropped the rest. Committed by a **manifest written LAST**: a directory without one reads as absent rather than as a half-written buffer (`world_model.pt`'s non-atomic write already cost this project one silent partial restore). Shape drift is **refused before the buffer is touched**, the same pre-flight discipline finding #74's F1 introduced. Written OUTSIDE `_wm_param_lock` — the acting thread takes that lock every step, so a multi-GB write inside it would stall the agent for the whole write. Capped per stream by `buffer_persist_max_gb` (8 GB ~ 14 h) because the instance footprint measured ~42 GB and the volume must not be filled.
- **W5. THE BODY COULD NOT FEEL MOTION.** Proprioception carried hunger, saturation, health, depth, has-tool, gui-open, hurt, carrying, swing streak and pitch — and **nothing for "am I actually going anywhere"**. For an agent whose *entire recorded failure history is a failure to move* — 96% of drive from staring at the sky, 10,149 consecutive steps in a villager's trade menu, 400 fruitless swings at an unreachable trunk — that is the most conspicuous missing sense. The adapter already read `xpos/zpos` every step to compute coverage, so the displacement existed the whole time and was simply never handed over.
  * FIX: `PROPRIO_KEYS` 10 -> 13 (`moved`, `head_sin`, `head_cos`). Displacement is computed in `_world_events` (already the stateful method) so `_proprio` stays a pure function of `world`; the anchor is cleared on reset, because a fresh world teleports the body and the first step must read 0 rather than "sprinted 200 blocks". Heading is sin/cos so the 360->0 wrap is continuous.
  * **A CONTRACT I VIOLATED AND THEN RESPECTED:** the first version emitted raw sin/cos in [-1,1]. `_proprioception_smoke` asserts every entry is normalized to **[0,1]** — a real invariant, and my two new dims would have been the only members on a different scale. Rescaled to [0,1] with unknown reading 0.5/0.5, matching the convention `pitch` already uses. The older test caught it; that is what it is for.
  * BLAST RADIUS: proprio reaches the **policy only** (the world model takes pixels), so no WM checkpoint is affected. The policy is discarded every launch by design and skills re-derive from goal slot_keys, so the width change is cheap.
- **checkpoint safety:** `batch_size`, `sequence_length`, `train_iters` and `buffer_capacity` are RUNTIME dimensions, not parameter shapes — unlike the 2026-08-14 scale-up, W1-W3 cost **no** brain state.
- **tests:** `tests/_data_diet_smoke.py` (22 contracts: the span-vs-60-ticks arithmetic as an executable assertion, replay-ratio band, horizon, buffer round-trip/wrap/shrink/cap/manifest-refusal/shape-refusal/multi-stream/fewer-streams, and the motion+heading senses). `_proprioception_smoke.py` updated 10 -> 13 with the rationale rather than a bare number bump.
